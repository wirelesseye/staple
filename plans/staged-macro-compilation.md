# Staged macro compilation

Replace the compile-time interpreter in `staple-compiler/src/macro_expand.rs`
with staged compilation: macro code, and everything it calls, goes through the
normal pipeline first. The compiled code then runs, and the code that uses the
macro is expanded afterwards.

This is the umbrella plan. Each phase below will get its own breakdown plan
before work starts. Line references are against `main` at `4d28a844`
(2026-10-31). Nothing here has been prototyped yet.

Don't refer to the plan files or phase numbers in the code and
documentation, except from the plan files themselves. Code comments,
`Staple.md` and diagnostics describe the behavior on its own terms.

## Where we are

- Expansion runs on raw syntax as the first step of name resolution:
  `NameResolver::resolve_program_inner` calls
  `macro_expand::expand_program_recovering`
  (`staple-compiler/src/resolve.rs:1939`). `staple expand` reaches the same code
  through `expand_macros` (`staple-cli/src/compile.rs:128`). After that comes
  `compile_program` (resolve, typecheck, ownership, specialization), then
  lowering and LLVM.
- Macro bodies, `def` helpers they call and `impl Parse` items are evaluated by
  `MacroExpander` (`macro_expand.rs:1917`, ~17k lines including `parse.rs` and
  `traits.rs`). It has its own value model (`Value`, with
  `Integer(i128, Option<IntegerType>)` at `:534`), its own permissive type system
  (`CompileType` at `:190`), and its own trait dispatch (`traits.rs`). Limits are
  a step budget and a depth limit (`MAX_EVALUATION_STEPS`,
  `MAX_EXPANSION_DEPTH`, `:21`).
- Compile-time items are removed after expansion (`macro_expand.rs:1845`), and
  the resolver keeps a list of them so it can reject run-time uses
  (`compile_time_items`, `resolve.rs:1874`).
- The standard library defines most of its control flow as macros in
  `stdlib/std/flow.sta` (`when`, `if`, `while`, `discard`, `for`) and its derives
  as modifier macros (`@derive_eq`, `@derive_hash`, `@derive_debug`,
  `@derive_default`). The flow macros avoid `if` in their own bodies (they use
  `match`), so they don't depend on themselves.
- `MetaType` (`macro_expand.rs:132`) describes macro *signatures* and drives
  argument matching (`match_macro_arguments`, `:11205`) and overload
  selection. That is a syntax-level job, not evaluation. It stays.

Why the interpreter has to go:

- **Integers have no width.** They are `i128` and dispatch as `{integer}`, so
  anything whose implementation depends on the exact numeric type (`USize`,
  ranges, `MemLayout`) can't be selected.
- **There is no memory model.** `Buffer`, `RawMutPtr`, `Gc` and
  `unsafe_read`/`unsafe_store` need real addresses and layouts. `List`,
  `String`'s storage, `Unique` and `Shared` all reach these.
- **It is a second copy of the language.** Every feature has to be built twice
  and kept in sync, and that cost keeps growing.

## Goal

When it is done:

1. A macro body is ordinary Staple code. It is resolved, type-checked,
   ownership-checked, specialized, lowered and compiled like run-time code.
   Anything that works at run time also works in a macro, including `List`,
   `String` building, ranges and exact integer types.
2. Expansion runs the compiled macro code on the host machine.
3. The interpreter is deleted. Only signature matching, hygiene, intrinsic
   macros and template macros (below) stay in the expander.
4. The language reference describes one language, plus a short section on
   phases.

## Decisions

These are proposals. Each one is confirmed or changed in the breakdown plan of
the phase that first needs it.

### 1. Phases are per item, and cycles are errors

Racket separates phases per module, and Rust uses a separate crate for
proc-macros. Both are too coarse for Staple: tests and user code often define a
macro and use it in the same module, and `std.flow` is used by the modules that
`std.syntax` imports.

- The **compile-time closure** of a macro is its body plus every item it reaches
  by name, transitively: helpers, types, traits, and the `impl` items those
  types and traits need (an impl is included when its trait and its self type
  are both in the closure).
- Items in a closure are expanded *before* the closure is compiled. They may use
  other macros, which forms a stage tower: to compile `m`, expand the macro
  calls in `m`'s closure, which may need to compile `n` first, and so on.
- If expanding an item in `m`'s closure needs `m` itself, or a macro whose
  closure contains that item, that is a cycle. It is reported with the chain of
  items, like `if` → `if_branches` → `String` → `String.drop` → `if`.
- An item generated by a macro can be in a closure, but only if the generating
  macro is in an earlier stage.

Closures are found by scanning unexpanded syntax and looking names up in the
expander's existing `ModuleScope`s, which already resolve macro names on raw
syntax. This over-approximates (a name inside a quotation counts as used),
which can only cause false cycles, never miscompiles. Quoted bodies are skipped
when they can be identified syntactically.

### 2. Template macros are expanded without compiling anything

A **template macro** is a macro whose body is exactly one `quote { ... }` or
`parse_quote { ... }` that only splices its parameters. The expander
instantiates it directly. It needs no closure and no compiled code.

This matters for two reasons:

- **Bootstrapping.** `std.flow`'s macros are used by almost every standard
  library module, including `String` and `List`. If `if` needed a compiled
  helper whose closure reaches `String`, and `String`'s code used `if`, that
  would be a cycle. `while`, `discard` and `for` are already templates. `if` and
  `when` get rewritten as overloaded templates that call themselves on the rest
  of their arguments (Phase 2).
- **Speed.** Flow macros make up most macro calls in a program. Instantiating a
  template is much cheaper than a round trip to compiled code.

Template-ness is a property of the macro body. It is not a separate `macro`
form. A macro that stops being a template only gets slower. Its meaning does
not change.

### 3. Compiled macros run in a separate macro-server process

Two options were considered:

| | In-process JIT (ORC via inkwell) | Macro server process |
|---|---|---|
| Data path | Handles into the expander's arena, no serialization | Arguments and results serialized |
| `panic`, abort, stack overflow | Crashes the compiler or LSP | Turned into a diagnostic |
| Non-termination | Needs a watchdog thread that can't stop the macro | Kill after a timeout |
| Build path | New JIT linking path, runtime `.ll` linked into JIT | Existing emit and link path, plus `-shared` |

**Recommendation: the server process.** The language server keeps expanding
half-written code, so a crashing or looping macro must not take it down. This is
the same choice rust-analyzer made with `proc-macro-srv`.

- The phase-1 program is compiled for the **host** triple as a shared library.
  Its entry points are one generated shim per macro.
- The server is the `staple` binary itself (`staple __macro-server`). It loads
  the library with `dlopen` and hands it a table of intrinsic function
  pointers at startup. Since the server already contains `staple-syntax`, the
  syntax intrinsics are plain Rust functions over real `Syntax` trees, and the
  child needs no extra runtime library.
- One server runs per compiler invocation (or per LSP session). Requests are
  batched by expansion round.
- An in-process mode that loads the same library can be added later as an
  optimization for trusted, cached libraries such as the standard library's. It
  is not part of this plan. Phase 0 found that an LLVM JIT is no faster to
  build and can't reuse cached objects, so that mode would use `dlopen` too.

### 4. Syntax values cross the ABI as handles

- `Syntax`, `UnstructuredExpr`, `UnstructuredType`, `UnstructuredPattern`,
  `UnstructuredItem`, `UnstructuredModifier` and `ParseStream` are already
  `@sized_opaque` (`stdlib/std/syntax.sta:93` and following). In compiled code
  they become a `U64` handle into the server's syntax arena. Copying a
  `ParseStream` copies its handle. The arena makes forks cheap (a stream is an
  immutable `(fragment, offset)` pair).
- The intrinsic ABI only carries scalars, handles and byte buffers. Structured
  syntax types (`Ident`, `CallExpr`, `Sequence`, `Separated`, `ProductType`,
  ...) are ordinary Staple data built *in Staple* by `std.syntax`. They use
  small non-generic intrinsics such as `__classify_expr: Syntax -> U8`,
  `__call_parts`, and `__ident_text`. The generic
  `__parse_primitive: <T> mut ParseStream -> Result<T, ParseError>`
  (`syntax.sta:296`) is replaced, since a host function can't build an
  arbitrary `T`.
- `quote` and `parse_quote` stay intrinsic macros. Inside phase-1 code they
  expand to ordinary calls. `quote { ... }` becomes
  `__instantiate (template_id, splices)`, which returns `Syntax`. `parse_quote`
  becomes `Parse.parse_all` applied to that result, so its contextual type is
  found by normal inference instead of the expander's special case. Template
  fragments are sent to the server when the library is loaded.

### 5. The parent owns hygiene, spans and syntax ids

The child keeps hygiene contexts and spans as opaque numbers that it copies but
never creates. A request carries the macro's definition context, so
constructed identifiers get the definition module's hygiene. The parent
renumbers syntax ids in every result (as `freshened_syntax` does today,
`macro_expand.rs:1017`) and applies the fresh expansion identity. Since the
hygiene rules stay in one place, Phase 5 can compare expansions token by token.

### 6. Limits

- The depth limit (128 nested expansions) stays in the parent.
- The step budget is replaced by a per-request wall-clock timeout, plus the
  stack-size and memory limits of the server process. The defaults and the
  diagnostic wording are decided in Phase 4.

### 7. Effects at compile time

The reference currently says compile-time evaluation "rejects external or
runtime-only effects". Compiled macros could do I/O. **Proposal:** link phase-1
libraries against a runtime without `std.fs`, `std.io` input, `std.process`
spawning or `std.rand` seeding from the OS, and report a use of those inside a
closure as an error. That keeps expansion deterministic, which caching and the
LSP depend on. `println` for debugging could be allowed and sent to stderr.
Phase 2 decides this.

### 8. Macro code runs on the host, so layouts are the host's

`MemLayout`, `USize` and pointer width inside a macro describe the machine
running the compiler, not `--target`. The same is true of Rust proc-macros.
Macros produce syntax, not target constants, so this is documented rather than
worked around.

## Phases

Each phase leaves `main` working, and the interpreter stays the default until
Phase 5.

### Phase 0: spike

Prove the risky parts before committing to them. The spike doesn't merge.
Breakdown and status: [`staged-macro-compilation-phase-0.md`](staged-macro-compilation-phase-0.md).

**Status (2026-11-03): done on macOS and Linux.** The result is go on
Decision 3. Libraries link with the existing runtime unchanged. A panic is
trapped without a restart. A timeout or stack overflow comes back to the
parent as an error. IPC costs about 7–10 µs per request. A closure builds in
1.6–2 s against cached std objects. Findings that change later phases:
phase-1 libraries must link cached std objects (Phase 4); the host table
thunks and the `exit` trap must be hidden external definitions; the JIT is
not worth pursuing.

- Compile a hand-written phase-1 program (one macro, one helper using `List`
  and `String`) for the host as a shared library with the existing
  lowering/codegen. Load it from a `staple __macro-server` stub and call its
  shim with a fake syntax handle.
- Measure: compile and link time for a small closure, server startup, and
  round-trip cost per call. Compare against interpreting `@derive_eq` on a
  large type.
- Confirm the runtime `.ll` files (`gc.ll`, `io.ll`, ...) can be linked into a
  shared library (PIC relocation model, no `main`, GC roots initialized from
  the shim).
- Output: go/no-go on Decision 3, and numbers for the Phase 4 caching design.

### Phase 1: phase-separation analysis (interpreter still runs)

Make the phase rules real before anything is compiled.
Breakdown and status: [`staged-macro-compilation-phase-1.md`](staged-macro-compilation-phase-1.md).

**Status (2026-11-03): done.** Closures, stage-ordered expansion, template
macros and cycle errors are in. Corpus expansion output is identical to the
baseline, apart from five standard-library files that were edited. The
interpreter no longer expands macros lazily; the one remaining lazy
expansion is in the static check (below). Findings that change later phases:
`if` and `when` stayed ordinary macros, with `compile_error` instead of `panic`,
so B3 did not get faster; `True`, `False`, `None`, `Some` and `Ordering` are
written by hand because the derive macros and `typegroup` reach them;
the analysis costs 8–20% on the expansion timings (about 25 ms of scanning),
so the "no slower" criterion is not met and Phase 4's cache should hold the
closures;
`MacroAnalysis` carries `closures` (for the macros that were invoked) and
`templates`, which Phase 2 reads. See the Phase 1 breakdown for the cycle
inventory and measurements.

- Compute compile-time closures and the stage order on unexpanded syntax
  (Decision 1). Report cycles with item chains.
- Drive the existing expander in stage order. Behavior should only change by
  reporting new cycle errors.
- Recognize template macros (Decision 2) and instantiate them directly. The
  interpreter is still used for every other macro. This is the first speed win,
  and it gives Phase 5 a cheap differential test.
- Make `if` and `when` closure-free, since `panic` reaches `String` and
  `String` uses `if` (done with a `compile_error` intrinsic; no template or
  repeated splice was needed). Find and break every other cycle in the standard
  library before cycles become errors (done: hand-written `True`, `False`,
  `None`, `Some`, `Ordering`).
- Spec: add a "Phases" section to `Staple.md`.
- Tests: closures across modules and packages, cycles, generated items in
  closures, template detection edge cases.

### Phase 2: make macro code compile as ordinary code (check only)

Every closure must pass the real front end. The interpreter still runs the
macros. The real pipeline only checks them.

- Add a check that sends each closure through `NameResolver` and `TypeChecker`
  as a standalone program, after expansion. Run it on the standard library and
  the macro tests. It is opt-in at first, then on in CI.
- Run the interpreter's static check (`validate_compile_time_code`) per closure
  after expansion instead of once over raw syntax. It still expands macros
  lazily, which Phase 1 could not remove because it runs before any expansion.
- Close the gaps the check finds. Known candidates:
  - The syntax types and intrinsics declared as run-time types with real
    representations (handles), including `Ident<"else">`-style singleton
    string types in patterns.
  - Compile-time-only semantics written in `Staple.md` that differ from
    run-time code. Examples: `?` that "leaves the innermost compile-time
    function with that value" for any non-`Result`, `return` from nested
    blocks, and `mut` parameters passed by address. Each one either already
    matches run-time behavior or gets changed in the language for both.
  - Places where the expander's permissive dispatch hid an ambiguity (integer
    width, unbound type arguments). Fix them in the source with annotations.
  - The special orphan rule for `impl Parse` (`Staple.md`, "Parsing syntax with
    `Parse`"). It becomes the normal orphan rule.
- Decide Decision 7.
- Output: a list of language changes, each landed with run-time tests. The
  inventory is the main deliverable of this phase's breakdown plan.

### Phase 3: syntax runtime

Make syntax values exist in compiled code.

- Server-side syntax arena and the intrinsic function table (Decision 4),
  written in Rust on top of `staple-syntax`.
- Rewrite `std.syntax`'s `Parse` implementations to use the non-generic
  intrinsics. Delete `__parse_primitive` and the `__*_group` intrinsics they
  replace.
- Lower `quote` and `parse_quote` inside phase-1 code to template-instantiation
  calls (Decision 4).
- Argument passing: the parent still matches arguments against `MetaType`
  signatures. It sends the *match tree* (atoms, sequence elements, present or
  absent options, delimiter contents) as handles. The shim generated for each
  macro builds the typed parameter values from that tree, with one decoder per
  parameter type, generated from its `MetaType`. Results come back as a handle
  plus the declared result category. `Sequence<Item>` results and emitted items
  come back as a list of handles.
- Wire format between parent and server: a versioned, length-prefixed binary
  encoding of `staple_syntax` trees with spans and hygiene numbers.
- Tests: Rust unit tests for the arena and the intrinsics, and Staple tests that
  run `Parse` implementations through a test harness without the server.

### Phase 4: building and running phase-1 libraries

- Synthesize the phase-1 program for a stage: its closure items plus one shim
  per macro (`extern "C"`, one symbol per macro, plus the template table).
  Compile it for the host triple through the normal pipeline, and link it with
  `-shared` against the restricted runtime (Decision 7).
- `staple __macro-server`: startup handshake (protocol version, intrinsic
  table), loading libraries, requests, timeouts, and turning `panic`, abort and
  crashes into diagnostics located at the invocation, with the macro's panic
  message.
- Build phase-1 libraries against the cached standard-library objects, as
  incremental package builds do. A whole-program build costs about 3.2 s
  even for an empty closure, against 1.6 s with cached objects. Most of what
  is left is the front end checking the standard library. Cache that, or
  check only the closure's modules.
- Caching: fingerprint each closure (its items' syntax, the compiler version,
  the host triple and active features) with the hashing that
  `staple-cli/src/cache.rs` already uses. Store libraries in the user cache
  root. Prebuild the standard library's macro libraries next to its objects
  (`<stdlib>/target/<host>/macros`) in `scripts/install-stdlib.sh`.
- Package builds: dependency macros are built once per dependency
  fingerprint, not once per dependent.

### Phase 5: switch over

- Add `--macro-engine=interp|compiled` (hidden). The compiled engine expands in
  stage order through the server, and template macros stay in the parent.
- Differential testing: run both engines on the standard library, every test
  in `staple-compiler/tests` (about 450 macro tests), and the examples. Compare
  the expanded syntax trees from `render_expanded_module`, normalized for
  syntax ids. Mismatches are fixed or documented as intended changes.
- Make `compiled` the default when the corpus agrees. Keep `interp` for one
  release cycle as an escape hatch.
- The LSP uses the compiled engine with recovery. If a macro fails to compile
  or run, its invocations stay unexpanded and show a diagnostic, and the rest
  of the file is still analyzed. Libraries are rebuilt in the background after
  edits, with debouncing. The old library is used until the new one is ready.

### Phase 6: delete the interpreter

- Remove `Value`, `ProductValue`, `SequenceValue`, `CompileType` and its
  helpers, compile-time trait dispatch (`macro_expand/traits.rs`), the
  evaluation half of `MacroExpander`, the step budget and the
  `Parse`-default stripping (`macro_expand.rs:1851`). Keep signature matching,
  overload selection, hygiene, intrinsic macros and template instantiation.
- Replace `compile_time_items` (`resolve.rs:1877`), which lists the
  `std.syntax` intrinsics so importing them is not an error, once those
  intrinsics change.
  Phase 1 already added `macro_expand/{templates, scan, closure, staged}.rs`;
  consider splitting what remains into `macro_expand/{matching, hygiene}.rs`.
- Remove `--macro-engine`.
- Spec: replace the "Compile-time evaluation supports ..." paragraph and the
  remaining-limitations list in `Staple.md` with the phase rules. Remove the
  statements about integers having no width for dispatch, and about ranges,
  `to_list` and `List`/`String` collection being run-time only.
- Expected size: most of the ~19k lines go away. Phase 3 and 4 code replaces
  part of it.

## Risks

- **Build time for user macros.** Every new or edited user macro costs a full
  compile and link of its closure. Mitigations: template macros skip this, the
  standard library is prebuilt, and closures are cached by fingerprint. The
  numbers from Phase 0 decide whether this is acceptable.
- **False cycles from over-approximate closures.** If they hit real code,
  narrow the scan (skip quoted bodies better, or resolve after a partial
  expansion) before adding escape hatches.
- **Semantic drift found in Phase 2.** Some interpreter behavior may not match
  run-time semantics. Every such case is a language decision. It is written
  down in Phase 2's plan, not resolved silently in Phase 5.
- **Platform support for `dlopen` and shared libraries,** including Windows
  DLLs. If Phase 0 shows that loading is too fragile, link each phase-1 program
  as an executable instead. That only changes the server's loading step.

## Open questions

1. Should a macro be able to declare that it is template-only, and get an error
   if it isn't? That would make the bootstrap guarantee explicit for `std.flow`.
2. Should the "Phases" rules let a module opt into coarser, module-level phases
   for clearer errors?
3. Compile-time I/O: is debug `println` allowed (Decision 7)? Should file reads
   like `include_str` ever be supported? If so, they need to feed into the
   cache fingerprint.
4. Does `staple expand` need a way to show which stage each item was expanded
   in, for debugging cycles? Phase 1 added the hidden `STAPLE_MACRO_CYCLES`
   environment variable, which prints recorded cycles; a public flag is still
   open.
